# AlwaysConnect 架构审查（2026-11-05）

起因：用户问"用到了好多组件，这么复杂，前面出了那么多问题，是不是站在错误的架构或地基上？有没有简单合理的解法？"
本文只做判断与建议，不改代码；结论供用户决定。

## 一、结论先说

是的，大部分问题来自地基，不是某几行代码写错了。归结为两点：

1. **我们在手工做系统本该替 VPN 软件做的事。** 正规的 Mac VPN 软件用苹果的 VPN 框架（Network Extension）：
   路由、DNS、断线保护都由系统管理，程序崩溃或被强杀时系统会自动还原。我们没有开发者账号，用不了这个框架，
   只能让一个管理员权限的后台服务、外加 shell 脚本，直接改全局路由表、系统 DNS 和防火墙（pf）。
   系统不会替我们回滚这些改动：每多一种改动，就要在退出、崩溃、强杀、更新、重启、睡眠各条路径上各写一遍"撤销"，
   漏一条就把用户困在断网里。两次断网和今天残留的隧道 DNS，都是这一类。

2. **为了"指定域名不走 VPN"，我们把系统叠到了最复杂的那个角落。** 这个需求同时碰上三个限制：
   Cisco 连接期间它自己的过滤器会挡掉一切不走隧道的流量（我们不能绕开）；公司证书的私钥不可导出，
   开源客户端拿不到；没有开发者账号，用不了系统的分流框架。于是只能"自己建隧道（openconnect）
   + 在 App 里做证书转接 + 再叠一层用户态分流核心（mihomo）"，三层都要改全局网络、都要自己收尾，
   彼此还会抢同一样东西（默认路由、DNS、出口），第 2 批的环路断网就是这么来的。

最简单、最稳的解法：**让 Cisco 负责网络，AlwaysConnect 只做"自动驾驶"；"哪些网站不走 VPN"
请公司 IT 在 Cisco 网关上配置按域名排除**（Cisco 原生支持，客户端里已经有这一项，目前是空的）。
这样不需要自建隧道、证书转接和分流核心，代码能删掉一大半，断网风险也只剩"断线保护"一处，而且可以收得很紧。

## 二、现在的组件

| 组件 | 规模 | 作用 | 是否改系统网络 |
| --- | --- | --- | --- |
| 菜单栏 App | 约 5700 行 Swift | 界面、驱动 Cisco 命令行、证书转接 | 否（转接只监听本机） |
| 后台服务（root） | 约 3700 行 Swift | openconnect 引擎、防火墙 pf、分流核心、看门狗、恢复 | **是**：pf、路由、进程 |
| vpnc-script（shell） | 约 230 行 | openconnect 建隧道时改路由、改系统 DNS | **是**：默认路由、主机路由、scutil DNS |
| 分流核心 mihomo（root） | 外部程序 | 第 2 批全机接管（已默认关闭） | **是**：0/1、128/1 路由、TUN 网卡 |
| Rust 核心 | 约 2600 行 | 会话状态机、pf 规则文本、规则引擎、Linux 测试绑定 | 间接（生成 pf 文本） |
| 透明代理扩展 + 数据泵 | 约 1400 行 | 按应用分流（需要开发者账号，从未启用） | 否（没用上） |
| 外部依赖 | — | Cisco Secure Client、Homebrew 的 openconnect 与 mihomo、系统 openssl | — |
| 脚本 | 20 多个 | 构建、安装、实测、恢复 | 部分是 |

改全局网络状态的地方有四处：后台服务（pf、路由、进程）、vpnc-script（路由、DNS）、分流核心（路由、TUN），
以及恢复工具（反向操作）。每处都有自己的一套撤销逻辑。

## 三、我们踩过的坑，按根因归类

1. **改了系统网络，异常时没还原**（地基问题，最危险）：
   异常退出后 pf 还在封网，整机断网（第一次）；开机时按上次残留状态封网（§23.12）；
   openconnect 被强杀后系统 DNS 和"主网卡"仍指向已不存在的隧道（今天）；更新后台服务后 openconnect 成了孤儿（§23.7）；
   退出没把进程收干净（§23.8、§23.11）。
2. **几层都想管同一样东西**（地基问题）：
   分流核心与 openconnect 都接管全局流量、绑定出口的路由缺失，形成环路，整机断网（第二次，§24.6）；
   防火墙规则掐断了装规则之前就建立的转接连接（§23.6）；Cisco 的过滤器让任何"按域名直连"都做不了（§22.1）。
3. **关键行为依赖外部命令行的真实表现**（结构性风险）：
   openconnect 调用脚本的方式（§23.5）、Cisco 命令行的提示与批准文案、openconnect 的认证模式、mihomo 绑定网卡的行为。
   这些只能在用户的真 Mac、真网关上发现，每次发现都可能伴随断网。
4. **没有开发者账号带来的绕路**（地基问题）：后台服务要靠管理员密码手工安装；不能用系统 VPN 框架；
   要在 App 里做 TLS 证书转接，才能让开源客户端出示钥匙串里的证书。
5. 普通的实现与界面问题（重复弹窗、开关颜色、图标、文案等）：正常迭代，不是地基问题。

前四类占了大部分时间和全部的断网事故。

## 四、可选方案

### 方案一（推荐）：Cisco 管网络，AlwaysConnect 只做自动驾驶

- **保留**：自动登录、批准提醒与超时自动重发、掉线自动重连、通知与掉线记录、家里局域网检查、一键恢复网络。
- **"哪些网站不走 VPN"交给公司 IT**：Cisco 支持在网关上配置"按域名动态排除"（Dynamic Split Exclude Domains），
  例如某些网站的域名；配好后由 Cisco 自己让这些流量走本地网络，我们不用写任何分流代码，
  也不会和 Cisco 的过滤器冲突。你的 Cisco 连接信息里有"Dynamic Tunnel Exclusion"一项（目前为 None），
  就是这个功能的位置，只差网关配置。
  你说过公司 IT 允许，那么请 IT 配这一项，比我们自己造一套分流稳得多。
- **删掉**：自建连接与证书转接、分流核心（第 2/3 批）、透明代理扩展与数据泵、只为这些服务的 Rust 部分。
  后台服务只剩一件事：断线保护（pf）。
- **断线保护再选一次**（需要你定）：
  - 保留：仍需 root 后台服务；按现在"网络闸门"的做法收紧（唯一写入点、最多封 2 分钟、开机不封、一键恢复）；
  - 去掉：彻底不需要 root 后台服务和管理员密码，App 变成一个普通程序，再也不可能把网断掉；
    代价是 Cisco 彻底掉线、重新登录的那几十秒里，流量会走本地网络。Cisco 对短暂网络抖动会自己续连，
    续连期间它是否仍拦截本地出口，还没实测过，去掉之前要先测。
- 速度：被排除的域名直接走本地网络，不再绕公司出口；其余仍走 Cisco 的 DTLS（UDP）通道，
  通常比自建连接只能用的 TLS（TCP）通道快（未实测对比）。

### 方案二（只在 IT 不同意配置时）：自建连接，但只用系统路由分流，不再叠第二层

- openconnect + 证书转接保留（这是不可导出证书下唯一可行的自建方式，已实测可用）；
  "哪些域名不走 VPN"改为：本机解析这些域名，把得到的地址加一条经本地网卡的主机路由（业界常见的 vpn-slice 做法），
  防火墙放行同一组地址。全程只有一条隧道、一个路由所有者，没有第二个 TUN，就不会再出现环路。
- 不支持按应用、按单条连接分流（这两样在没有开发者账号时必须靠用户态核心，正是第 2 批出事的那层）。
- 必须同时做第五节的"改动台账"，否则还会重复第三节第 1 类问题。
- 缺点：仍依赖 openconnect 与转接，只能走 TLS，速度不如 Cisco；工作量中等。

### 方案三（长期）：开发者账号 + 苹果 VPN 框架

- 每年 99 美元。系统接管路由、DNS 与断线保护，进程崩溃自动还原，原生支持按应用、按域名分流。
- 但要把整个连接重写成系统扩展（还要把 openconnect 编进扩展），工作量最大；
  而且在 Cisco 连接期间同样绕不开 Cisco 的过滤器，所以它只对"自建连接"有帮助。

## 五、不论选哪条，都应该做的底层修正

1. **改动台账**：任何对系统网络的改动（路由、DNS 条目、pf 锚点与开关引用、我们起的进程）在动手前先记一笔，
   只用一个"全部撤销"的例程按台账倒着还原；退出、崩溃后重启、开机、一键恢复都调用同一个例程。
   这样"漏了哪条路径没收尾"这类问题从根上消失（现在是四处各写一套撤销）。
2. **会动网络的测试一律自带自动回退**：连通性探测失败即撤销改动，不需要用户在断网时找人。
3. **删掉不用的组件**：透明代理扩展、数据泵、未用的规则引擎与 Linux 侧绑定，降低构建、测试和理解成本。

## 六、需要你决定的事

1. 走哪条路：方案一（推荐）、方案二，还是方案三。
2. 如果选方案一：愿不愿意请公司 IT 配置"按域名动态排除"（我可以帮你写给 IT 的说明，列出要排除的域名）。
3. 如果选方案一：断线保护保留（需要后台服务）还是去掉（不再需要管理员权限）。

在你决定之前，我不会继续第 2、3 批，也不删任何东西；自建连接与分流核心维持现状（核心默认关闭）。
